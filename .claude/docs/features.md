## web/ — public site (Nuxt 4 + Nuxt UI v4)

No `layouts/` dir; the shell is `web/app/app.vue` (`AppSkipLink`, `AppHeader`, `NuxtPage` inside `UMain`, `AppFooter`). `UMain` is the page's only `<main>` (`#main-content`); page components use a single non-landmark `<div>` root (#1615). **Dark-only** — no colour-mode toggle; the colour-mode `storageKey` was moved so stale `light` preferences retire.
All data goes through the catch-all proxy `web/server/api/[...path].ts` → `NUXT_API_BASE_URL`.

### `/` — `web/app/pages/index.vue`
Hero + search field, **two** live stat chips (main games analysed, truemains tracked), a tier-list teaser (`home/TierlistPanel.vue`, top 8, a ranked table — #, champion, lane in its own centred column, tier, WR coloured on the data axis, pick rate as a `UProgress` bar on one scale — under a "Strongest picks" label whose "Full tier list" link replaced the footer button, rendered eagerly with `home/TierlistPanelSkeleton.vue` while loading), a global truemains teaser (`home/TruemainsPanel.vue`, top 7, rank crest + hover tooltip like the leaderboard, no region filter), a **desktop app beta banner** right under the hero, above the two teasers (`home/DesktopBetaPanel.vue`, #1719/#1725 — Beta badge, "TrueMain, on your desktop.", "Get the beta" to `/download`, and a whole capture of the app's dashboard, `public/desktop/dashboard.webp`, beside the text — on the page background, not in a card), CTAs. Both chips and the teaser read `GET /champions/overview` (`useChampionOverview()`, #972) — a homepage-sized snapshot (games-analyzed total across every aggregated row, not just the ranked ones; pre-sorted top rows) instead of the full `/champions` directory.
**Both chips are lifetime totals, printed compactly and without a patch qualifier**: `gamesAnalyzed` is one SQL `SUM` over the light per-patch record (`champion_patch_stats`, the scopes summed per patch — #1957) on the tracked queue, all patches, so it survives the full aggregates keeping two patches (`GetTotalGamesAsync`, cached 30 min), and the truemains count is the leaderboard's global total. `formatCompactCount` (`shared/utils/counts.ts`) shortens them — `490,365` → `490k`, `1,204,886` → `1.2M` — always rounding **down**, so the printed figure is one the data clears. The teaser below stays on the served patch alone: a tier is a percentile inside one patch's field. The former third chip ("N champions ranked") and the patch-window labels (`over 16.15–16.14`, #1109) are gone — see `decisions.md`.

### `/champions` — `web/layers/common/app/components/page/Champions.vue`
Shared with the desktop app (#1732): the route file `web/app/pages/champions/index.vue` only adds the head tags.
Champion/lane directory, one row per (champion, position) — capped at each champion's **two dominant lanes** (#1082, see below), so ~270 rows rather than 5 × N. Filters: role, champion, elo, **truemains**, patch — the `Champion/ListFilters.vue` row it shares with the tier list (#2032). Elo defaults to **Master+** (#1346, `DEFAULT_ELO_BRACKET`), not "All ranks"; the resting URL carries no `?elo=` and picking "All ranks" pins `?elo=ALL`, which is now a deliberate choice rather than the absence of one.
**The default patch is the newest one that can actually fill a directory (#1109)**, not simply the newest one holding an aggregate row: a patch needs `ChampionsList:MinServablePatchLines` (50) `(champion, lane)` lines past `MinSampleGames` before the patch-less reads default to it, and the resolver walks back a patch at a time until one clears the bar. Shared by the directory, the tier list and the homepage, all of which resolve through `ChampionSummariesQueryService`. The served patch is reported in every row's `patchVersion` and drives the patch picker, so the fallback is visible rather than silent, and the thin patch stays explicitly selectable. Set the bar to 0 to restore the pre-#1109 rule. The champion page applies its own, per-lane bar on top of it (#2249, below). A **`UTable`** (#1726, #1734, `Champion/DirectoryTable.vue`): `#` (place in the current order across pages), champion, lane, tier, runes (keystone + secondary tree), core build path (6 items max), WR/PR/**BR** (whole percents, #1738), games. **Tier, WR, PR, BR and games sort from their headers**, both directions (`?sort=` / `?order=`, absent at the default pick rate descending). The page reads **one page at a time from `GET /champions/directory`** (`useChampionDirectory`): lane, champion, order and page are API parameters, so the browser never holds the whole directory. The table is an `@container` and drops columns as it narrows: phone keeps `#`, champion, lane, tier, WR, PR. A line opens the champion page (click, Enter/Space; Ctrl/Cmd-click for a new tab); the cold load shows placeholder lines through the real columns.
**BR (ban rate, #920)** is lane-independent — the same value on every row of a champion — and shows an em dash, never `0%`, on patches predating ban ingestion. Tiers are pickRate + banRate + winRate, weighted toward presence (pick 45% / ban 30% / a sample-shrunk win rate 25%) and ranked by percentile within each lane — see `ChampionTierCalculator` (#971).
**Dominant lanes only (#1082)**: `ChampionDominantLaneFilter` keeps each champion's `ChampionsList:MaxLanesPerChampion` (2) most-played lanes, and a *secondary* lane only if it carries `ChampionsList:MinSecondaryLanePlayRate` (10%) of the champion's games. The most-played lane is always kept, so no champion disappears. Applied in `ChampionSummariesQueryService` after the sample floor and **before** tiering, so it lands identically on `/champions`, `/champions/tierlist` and the homepage teaser, and a lane's tier percentiles rank only the champions genuinely played there.
Pagination, lane and champion filters and the order are **server-side** since #1734 (`PAGE_SIZE = 50`; a page past the end steps back to page 1). Body wrapped in `<ClientOnly>` with the skeleton table as fallback; all fetches `server: false` deliberately (hydration-mismatch fix, #149).

### `/champions/tierlist` — `web/layers/common/app/components/page/TierList.vue`
Shared with the desktop app (#1732): the route file `web/app/pages/champions/tierlist.vue` only adds the head tags.
Server-computed tier list, over the same dominant-lane rows as the directory (#1082 — a champion appears at most twice, on its two dominant positions) and carrying **the directory's own tier**: since #1240 the endpoint only regroups the `Tier`/`TierScore` `ChampionSummariesQueryService` already stamped per lane, instead of running `ChampionTierCalculator` a second time over the same rows with the same options. The two endpoints can therefore no longer disagree on a champion's letter — an integration test compares them row by row. One `SectionCard` per tier group (S→D), each a wall of champion portraits linking to the champion page (`ChampionTierChip`). Header and filters are **the directory's, control for control** (`PageHeader` + the one `Champion/ListFilters.vue` row both pages render, #2032: role left, champion search centred, rank / **truemains** / patch grouped right; only the directory's resets `?page=`) with the same Master+ default; the champion search narrows the tier cards to that champion's lines client-side (`?championId=`) and hides tiers left empty. A chip is the portrait alone, with its lane badged into the bottom-right corner; the name and `Win rate / Pick rate / Ban rate` live in the hover tooltip, values coloured on the `--color-data-*` axis by `app/utils/rate-tone.ts` (same ban-rate caveats as the directory). The link's `aria-label` carries name + lane + the three rates, since no tooltip opens on touch or for a screen reader.

The dominant option of every category is in the core block regardless, which is why the single-option card was a restatement rather than an alternative. Both caps are shared with the `?vs=` matchup fold since #1240 — they were 4 tabs / 3 variations on the aggregate path against 3 / 5 on the matchup one, so picking an opponent silently removed a tab and added two variations, as if the filter had changed what a build is. The caps describe the component, not the data source; the aggregate path's values won, because a matchup slice holds 4 games at the median and a fourth or fifth variation there is a single game rendered as a trend. Still literals for now — #1241 migrates the build thresholds to `ChampionsListOptions`. While the aggregate is in flight the section renders `Champion/BuildTabsSkeleton.vue`, which is **these same tabs in `pending` mode** over a placeholder aggregate (`app/utils/build-placeholder.ts`): the loading picture is the loaded layout with unresolvable ids, so every icon shows the pulsing box `SkeletonImage` already draws while a real icon loads and every number is masked. The two loading phases the page cannot merge (waiting on the API, then waiting on the ~95 DDragon icons) therefore look like one continuous state instead of two different pictures — see decisions. `Champion/BuildCoreSkeleton.vue` is the core-view-only counterpart for the composition builder; `pages/dev/build-skeleton.vue` renders both with nothing to fetch. Each panel (`Champion/BuildPanel.vue`) contains:
  core section (spells, starter items, skill order, boots, build path, runes), **build tree**, **variations** and **rune variations**. Power spikes were removed (#1599).
- **Why this item** (#1451) — every item hover card on the page (`GameTooltip/ItemBody.vue`) carries the **situational build context** measured by #1450 under the item's own tooltip: a class line — `Situational` or `Core item` — and, when situational, up to three lines of the shape *"Against a magic-damage team"*. Deliberately just the situation: the rate (#2256), the contrast rate, the sample size and the scope footnote were all cut (#1465) because the class already says the pick is situational and the card is read in a hover, not studied. The **key term carries the item tooltip's own colour vocabulary** — magic damage in the magic-resist cyan, physical damage in the armour orange, following Riot's rule that damage is coloured by the resistance that blocks it (`tooltip-parser/tag-classes.ts` is the source of that convention); terms with no stat behind them — melee, ranged, a strong laner — stay uncoloured, because a card where every other word is tinted says nothing. A `Preference` renders **nothing at all**: true, but not worth a line on three quarters of all items. The wording of every axis lives in `shared/utils/item-context.ts`; an axis this build has no phrase for is dropped rather than printed raw, and a vitest suite fails when the fold gains an axis with no copy for it. The low end of an axis is worded as its own situation — an ability-power item built when the allies lack it reads *"When your team lacks magic damage"*, never a negation — and a finding only ever sits on the end the item answers (`ItemContextWhitelist.Answers`, #2256). A card is looked up by slot **and branch and item** (`itemContextKey`), because the same item after a different parent is a different decision (#1496); the tree has the parent for free, the build path takes the item before it, and boots and starters use branch 0. The cards reach the **build tree**, the **core view**'s build path, boots and starter, and the **boots / starter variation rows**; tree nodes carry no mark of their own (#1465 removed the situational ring). One fetch per tab set (`useChampionItemContext` in `Champion/BuildTabs.vue`) rather than one per tab, keyed on (champion, position, patch) and deliberately not on rank or opponent.
- **Build summary** (`Champion/BuildSummary.vue`, #1123, typeset in #1143, hover cards in #1147, collapsed in #1466) — the build **in words**, at the **foot** of the right sidebar (below Truemains and Compare with mains) inside a **closed native `<details>`**, and the only build content in the server-rendered HTML (every panel around it is `server: false`). Sentences come from `shared/utils/champion-build-summary.ts`; the ids are resolved to names by `server/api/champion-summary/[championId].get.ts` (5 min `defineCachedFunction` — an hour until #1273, which was long enough for the prose to name a different patch, and a different sample, than the live panels beside it — ~3 kB payload — ~1 kB of names plus one icon URL each, 844 B gzipped) because naming an item needs the ~373 KiB client-only item map. Describes `builds[0]` — the tab the page opens on — and carries the **same scope as the panels**: the `?vs=` matchup filter is forwarded (without it the prose described the global build under panels re-sliced to the matchup) and `minSampleMet: false` adds the low-sample caveat the header shows as a warning dot. Every sentence is a measurement: a clause whose data is missing is dropped, an id DDragon doesn't know is dropped rather than labelled, and the whole section renders nothing when there is nothing to measure. Visible, never `sr-only`. #1143 gave it relief: the sentences are built as **tokens** (`championBuildSentenceTokens`), so every named entity renders with its own 16 px icon inline and a tone — items gold, runes in their tree's colour (`--color-rune-*`), measurements set bold and tabular — and no sentence uses an em dash. The plain sentences are the tokens concatenated, so the decorated paragraph and the indexable one cannot drift. Each mark (`Champion/BuildSummaryMark.vue`) also triggers the **same hover card as the icon grid** — item, rune, summoner spell and ability — resolved client-side from the static maps the page already fetches, so the payload doesn't grow and the cards simply appear at hydration. Rune *trees* and the pinned opponent get no card here: the tree card elsewhere (`GameTooltip/PerkStyleIcon.vue`, name plus CDragon's one-line summary of the path) would add little to a sentence that already names it. #1466 then cut the runes, skill-order and summoner-spell sentences — each named in words a row of icons already on screen — and closed the section by default: native `<details>` rather than `UAccordion`, because Reka unmounts closed content and the paragraph has to stay in the SSR HTML. ~110 words on a well-covered champion — short of the 150-300 the issue estimated, because the remaining words would have been padding rather than data. **Matchup sentences** (#1954): the paragraph closes with the lane's three best and three worst matchups, each with its record ("Azir (won 60.0% of 257 games)"), the second sentence worded around "counter". They are the first rows of the Matchups panel's own lists (the panel the player-scoped page still shows) — one ranking, `shared/utils/matchup-ranking.ts`, ranked at the panel's size and then sliced — read by the same cached route *after* the champion fetch, on the lane and patch it resolved (`shared/utils/champion-matchup-summary.ts`); skipped when an opponent is pinned. Each opponent is a link to its champion page (`BuildSummaryMark`). Rationale and the SSR round-trip trade-off in `decisions.md`.

A third **ban rate** chart appears only once at least two patches carry ban data (#920); its series is filtered to those patches rather than drawn with gaps.

The strip is washed red on the losing left to blue on the winning right, the match rows' result colours (`RESULT_SPREAD_WASH` in `result-tone.ts`). Best teammates ranked by *observed − expected* win rate (never raw pair WR), with a `RolePicker` narrowing the partner lane (the champion's own lane is excluded). Picking a partner expands the best third picks for that duo underneath. The *observed − expected* definition is the `Synergy` column header's tooltip — the card carries no subtitle or method footnote (#1699). Every row carries its sample, with how often the pairing actually happens in the games tooltip; the three insufficient-sample cases (no champion baseline / no partner past the shared-games floor / duo too thin to split) each get their own sentence with the real count — no fallback numbers. **Two more floors since #1090**, after the panel's best synergies turned out to be 21-game pairings led by "Sylas BOTTOM": `ChampionsList:MinSynergyPlayRate` (1% of the champion's games, combined with `MinSynergyGames` by taking the larger) drops pairings that are merely rare, and `ChampionsList:MinSynergyPartnerLanePlayRate` (10% of that partner's ally games across all lanes) drops pairings whose partner does not play that role at all. The ranking lives in `shared/utils/matchup-ranking.ts`, shared with the build summary's matchup sentences (#1954). Server-side, the panel (and Synergies) render their **skeleton**, never their empty state: the fetch is client-only, so an `idle` status counts as loading — it used to fall through to "No matchups with enough games on this lane yet", which is what a crawler indexed. The `?opponent=` search is served from the same aggregate rows as the list with **no floor at all**, so the two can no longer disagree on the same matchup (they did, 22 vs 13 games) and lane counters can no longer outnumber the games they sit next to. Only the player-scoped route stays live and cross-patch (the aggregate has no account dimension, and a patch filter would empty a single player's panel); it never lends the population-wide aggregate's lane counters to a player's row, and judges the player's own lanes from their 15-minute snapshots instead (`Matchups/PlayerLaneOutcomes.cs`, no decided-lane floor). **Mains comparison** (`Champion/MainsComparison.vue` — enter a Riot ID, compare WR/KDA/CS·min/gold·min against all mains or one chosen main).
- **Truemains toggle** (`Champion/TruemainToggle.vue`, #1346) — sits next to the rank select on the champion page, the directory and the tier list. **On by default**: the numbers are folded only from *mains* of the champion, which is the population the aggregate held exclusively before #1346. Off (`?everyone=1`, `?truemainsOnly=false` on the API) widens to every tracked player with games on the champion — a strict superset, not a swap. **The non-main rows only exist once `MainAnalysis:AggregateNonMainPopulation` is turned on** (default false, #1349): until then both states return the same games, because the pipeline still folds mains only. Carries the `AppLogo` M-check mark drawn at icon size in `currentColor` (never the rose-gold ramp: a gradient that stays lit would keep reading as "on", and its own `<defs>` id would collide with the logo's), with the label beside it so the control still reads without knowing the brand, and a **two-part `UTooltip`** (its `#content` slot, the `RateBadge` idiom — not the flat `text` prop): a title naming the population currently shown (`Truemains only` / `Every tracked player` / `Locked to truemains`) over one line saying what it is and what flipping it does, so a reader who only takes the title still learns which games they are looking at. It **locks on while a matchup is pinned** — that slice comes from a mains-only aggregate, and the API 400s the combination rather than serving mains-only rows under an "everyone" label; the filter composable also resolves the pair away, so a hand-edited `?vs=…&everyone=1` renders the matchup instead of erroring. Not rendered on the player-scoped champion page: its scope is already one account. The population is part of every cache key it touches — `useChampion`'s data key (without it the toggle flips with no refetch and the two populations share an entry), the SSR build-summary route's, and the backend's summaries cache.
- **Header population** (#1466) — the stat line names the cohort the counts come from (`824 games played by mains` / `across all tracked players`), so the truemains toggle (#1346) is legible without hovering its tooltip. **Only where a toggle exists**: the prop has three states, and the player-scoped page passes none, so it prints no cohort phrase at all. That third state needs an explicit `undefined` default (#1498) — Vue casts an absent boolean prop to `false`, which had the player page announcing `across all tracked players` over one account's games.
- **Matchup filter** (#923): an opponent picker sits in the filter bar next to role/elo/patch (`?vs=<championId>`), and picking one **re-slices every build section** — variations, core, build tree, runes, skill order — from the games where the two champions actually met. It is not an aggregate read: `champion_matchup_stats` has the opponent but no build data, and the pattern aggregates have the build data but no opponent, so this path folds `match_participants` live (`ChampionMatchupBuildsQueryService` + `LiveBuildVariationAggregator`, sharing `ParticipantBuildFactsLoader` with the `/matchup` tool so a game means the same build to both). The core moves with the slice because it *is* the most played value inside it, and the fold serves **the same 4 tabs / 3 variations** as the unfiltered page (#1240) — the filter changes which games are counted, never how much of the build is shown. Note the one cap that still differs on purpose: the matchup fold applies **no 5% pick-rate floor** (2026-07-30 — the honest answer to a thin slice is its game count, not a hidden section). Selecting an opponent pins the displayed position (the backend matches both sides on it and 400s without one); a matchup with no game in the retained window renders the no-data state. Every variation carries its game count — measured on production, the median champion-vs-opponent pair holds 4 games on a patch, so the volume has to travel with the percentages; it now rides in `RateBadge`'s hover tooltip — Games / Pick rate / Win rate on their own labelled line each — rather than sitting inline next to the two chips, which kept the rows scannable without losing the sample.
- States: `noDataForRank`, `notEnoughData`, low-sample alerts, and a watcher that reconciles the URL when the API drops a dead filter.
- **Share** (#926): `ShareButtons.vue` in the header of the populated state (copy link / native share / X), plus a dynamic OG card (`OgImage/Champion.satori.vue` — portrait, tier letter, WR/PR/BR tiles, sample and patch). See the *Share cards* entry under Cross-cutting.

### `/matchup` — `web/layers/common/app/components/page/Matchup.vue`

A **live matchup tool** (reworked by #921, renamed from `/builder` by #939 — the old route still redirects, query preserved), not a build editor. ## admin/ — operator portal (standalone Nuxt app, `ssr: false`)

Separate app with its own deployment and domain — **not** a `/admin` route of `web`.

**Auth & backend access.** Single-operator username/password → sealed httpOnly session (`nuxt-auth-utils`); no user store, no roles. `admin/server/api/auth/login.post.ts` does a constant-time compare with a per-IP throttle (5 attempts/60 s). Every route is gated by `admin/app/middleware/auth.global.ts`, which sends a signed-out visitor to `/login?redirect=<the page and query they asked for>`; signing in returns them there (#2289). The redirect goes through one sanitiser (`admin/shared/utils/login-redirect.ts`): only a same-origin relative path that is not `/login` survives — `//host`, `https://…`, backslash or whitespace tricks and `javascript:` fall back to `/`. That middleware only runs on navigation, so an **expiry while parked on a page** is caught instead by a global `$fetch` interceptor (`admin/app/plugins/session-expiry.client.ts`): a 401 from `/api/ops/*` or `/api/static/*` clears the session and redirects to `/login` (carrying the same `?redirect=`, so signing back in returns to the page and tab the session expired on) once, however many panels were mid-flight — before #1225 the dashboard just turned red with "Failed to load" and read as a backend outage.
**All backend traffic goes through one proxy**: `admin/server/api/ops/[...path].ts` requires the session, then forwards to `${opsApiBaseUrl}/ops{path}` injecting the secret `X-Ops-Key` **server-side** — the ops key never reaches the browser. Its containment guard (`server/utils/proxy-path.ts`, the same file in `web/`) rejects a path that could leave the backend, judged on the decoded path as well as the raw one. A boot plugin refuses to start outside dev with default credentials, short secrets, or an admin password under 12 characters.

**Instant navigation (#2306).** Every ops read (`useOps`) is stale-while-revalidate across navigations through one in-memory cache (`app/utils/ops-cache.ts`, 10 min TTL, 200 entries): returning to a page draws its last payloads at once — no skeleton — and refetches behind them; a payload under 5 s old is drawn without a request. `useOps`' `pending` means "nothing to draw yet" (skeletons), `refreshing` a request in flight (the navbar refresh spinners). A failed revalidation keeps the cached content under the page's single `FetchErrorAlert`, and a cached payload older than a minute whose revalidation has not landed gets one corner label, "Showing figures cached N min ago" (`OpsCacheAgeNotice`, in the default layout). Hovering or focusing a sidebar entry warms the main reads of `/`, `/health`, `/aggregation`, `/database` and `/configuration`. Live-refresh panels keep their 30 s cadence (a tick always hits the network), and the cache is emptied whenever the session ends — logout or the session-expiry sign-out (`plugins/ops-cache.client.ts`) — so no payload outlives its session. The DDragon champion list rides the same cache without revalidation.

**Open on the site (#2291).** One small external-link icon button, `components/SiteLink.vue`, opens in a new tab (`rel="noopener noreferrer"`) the public page of what the operator is looking at: the known-player edit panel and each column of a conflict's comparison → `/players/{slug}` (not for a removed player); the Trace tab's identity card and the candidate slide-over → the profile `/truemains/{Name-TAG}` (hidden without both halves of the Riot ID); each `/champions` row → `/champions/{slug}`. The paths come from the site's own builders (`web/shared/utils/truemain-path.ts`, `champion-slug.ts`) through `shared/utils/site-link.ts`, and champion slugs from `/api/static/champion-slugs`, which lives in `web/layers/nitro` since then so both apps read one map (numeric id while it loads; the site redirects it). The origin is `runtimeConfig.public.siteUrl` (`NUXT_PUBLIC_SITE_URL`): `https://truemain.lol` on prod, the stack's `PREPROD_SITE_URL` on preprod; unset (local dev) hides every button.

**Charts.** `nuxt-charts` (Unovis), referenced as `<Nc*Chart>` (`nuxtCharts.prefix`). The rule for picking a
mark lives in `app/utils/charts.ts`: a **flow** counted per period gets vertical bars, a **stock** (a level at

## backend/ — .NET 10 solution

### Api
Four controllers, all delegating to injected `I*QueryService` — no EF types cross the controller boundary; read models are `sealed record`s under `Api/ReadModels/`.

- **`ChampionsController`** (public): list, tierlist, `overview` (#972 — homepage snapshot: lifetime games-analyzed total + top rows), detail, trend, matchups, synergies, synergies/trios, scaling (read from the `champion_scaling_stats` fold since #1368; the uncalled `item-timings` endpoint was removed), mains-comparison, `POST composition-build`, and `POST composition-build/games` (#940 — the recommendation's provenance drawer, paged); both take an optional `player` Riot ID that samples that player's games alone (#1987, 404 when unknown).
- **`ChampionDraftController`** (public, #1674/#1675, reworked #1906): `POST champions/draft` — the desktop companion app's draft assistant. Resolves which enemy champion holds which lane (an assignment problem solved by exact enumeration of the ≤120 placements, priors from the ally synergy baselines decaying over four patches, a logistic confidence where 0.5 is a coin flip; user pins are hard constraints, ties break towards the placement on screen) and ranks the player's candidate picks by measured win-rate deltas kept separate in the response: the **lane** matchup (each placed enemy weighted by the solver's probability that it is our opponent, not the top guess alone), **blind safety** for the part of the lane still unknown (deltas into the opponents still available weighted by their play on the lane, plus how many of the 8 most played it is clearly behind into), the champion's own **strength** at the lane (its win rate there minus the lane average), the **enemy team** off our lane (#1713, observed minus expected against each enemy from `champion_opponent_stats`, weighted by the chance it is not our lane opponent — returned as `enemyDelta`/`enemyGames`, weight 0 in the score until the back-test has the backfilled data), the **team composition** once three allies are on the board (the pick's win rate when its allies' magic share and frontline count sit in the board's band, minus its win rate overall, from the item-context fold's `champion_item_context_totals` on `AllyMagicDamage` / `AllyFrontline`, the board placed by the fold's own `DraftAxisEvaluator` — `teamFitDelta`/`teamFitGames`, weight 0 until a back-test sets it, stated as a `teamFit` reason meanwhile), and the **mean** synergy with the allies on the board (hovered allies at half weight, flagged tentative). The ranking key shrinks each delta by its games (`delta × n/(n+k)`) and weighs lane, then strength, then synergy (k = 400, weights 1 / 0.5 / 0.25, settled by the back-test); `reasons` carries the 2–3 score terms behind each pick as text-free data (`laneMatchup`, `blindSafety`, `laneStrength`, `synergy`), then the facts that are not score terms (`lanePhase`, `teamFit` with its `axis`/`bucket` codes), and `thinSample` is a display flag. Reads the current patch with the previous one as a per-champion fallback, never every stored patch; the desktop sends the player's tier and above as `eloBracket`. `POST champions/draft/bans` (#1906) ranks bans by how far the player's declared pick — or their mastery-weighted pool — is behind into each lane opponent, times that opponent's share of the lane; never an ally's hover or lock; with nothing to protect, the lane's most banned champions labelled by ban rate. `Api/Services/Champions/Draft/`; the scoring arithmetic is `Core/Lol/Draft/DraftScoring.cs`, shared with the back-test `backend/Tools/DraftEvaluation`.
- **`ChampionNextItemController`** (public, #1749): `POST champions/{id}/next-item` — the desktop app's in-game "what do I complete next". The body is the live game (lane, items held in completion order, the nine other champions with their lanes when known, the enemies' inventories in game — #1750, the in-game axes of what they have built, through the fold's catalogue and Data Dragon item stats; none in champion select — optional gold lead at 15); unlaned enemies are placed around the given ones by the draft's lane solver. The answer, per open slot (next legendary, boots), is the candidates of the branch the build stands on, ranked by the share the mains take in a game like this one, with the base share, games, wins and the up-to-three situations that moved each item, and its `route` (#2183): the components in the order the mains buy them, each with id, cost, rank, share and `measured`, an intermediate's own components nested, from `champion_item_component_orders` (`Api/Services/Champions/ItemRoutes/`: the served patch, reaching back up to two patches until an item holds 20 games, else the recipe's order). `GET /champions/{id}/item-context` carries the same paths as `routes` for every build item and boots, for the site to show later. A lookup in `champion_next_item_terms` plus arithmetic (`Data/ItemContext/NextItemScorer.cs`); the champion's model and the patch's profiles are cached per aggregation version. `Api/Services/Champions/NextItem/`.
- **`ItemClassesController`** (public, #2203): `GET items/classes?patch=` — the in-game shop's classes of every item (`Fighter`, `Marksman`, `Assassin`, `Mage`, `Tank`, `Support`, main class first), read from each `ItemData` entry's `mItemAttributes` bits in CommunityDragon's dump of the game's item bin (`game/items.cdtb.bin.json`, ~16 MB) by a singleton `CommunityDragonItemClassProvider`, once per patch (the `latest` branch when the patch is not published yet, probed again after 30 min); `latest` when no patch is asked. For the desktop kit editor's picker; on the shell's `api_get` allowlist. `Data/Statics/`.
- **`ChampionDamageProfilesController`** (public, #1905): `GET champions/damage-profiles?patch=` — every champion's measured damage profile for the served patch (newest profiled one when omitted), one payload for the desktop draft's team damage bars: per `(champion, lane)` and one champion-wide entry (`position: null`, its best-covered lane) — the item-context fold's own snapshot (`ChampionProfileSnapshotRules`: lookback 2 patches, floor 100 games), so the bar and the build advice cannot disagree — with physical / magic / true shares summing to 1, `damagePerGame` (the team weight), the patch actually used, the split by build archetype (`builds`, archetypes above the floor) and `flexDamage` (two opposite-damage builds each ≥ 20% of the games). A champion the snapshot does not resolve comes back as `source: fallback` with a `damageClass` (physical / magic / mixed, from Data Dragon's attack/magic ratings) and no shares, or not at all. Cached per aggregation version. `Api/Services/Champions/Profiles/`.
- **`DesktopTelemetryController`** (public, #1805): `POST desktop/telemetry` — the desktop app's usage counts, reached through the site's `/api` proxy. Install id (GUID), version (`0.3.1` / `0.3.2-beta.4` shape), OS, first-launch flag, bounded counters; page and feature keys outside `DesktopTelemetryCatalog` are dropped, not rejected (a newer app under an older API). Folded with `$inc` into the install's document for the UTC day (`Data/Desktop/DesktopTelemetryStore.cs`). 202, write-only. Its twin **`DesktopDownloadIngestController`**: `POST internal/desktop/downloads` (log-ingest key, never through the public proxy) — one installer download, `$inc` into the day/platform/version counter. - **`OpsController`** (`X-Ops-Key` auth): 28 endpoints backing the admin portal.
- **`PlayersController`** (public, #2016): `GET players` — slug + last update of every known player with a tracked account, the sitemap's source (#2018); `GET players/{slug}` — a known player, their links and every listed account with the leaderboard's rank and top-mains cells (`Api/Services/Personas/PersonaQueryService.cs`, reusing `LatestRankSnapshots` and `LeaderboardPageHydration.FetchTopChampionsAsync`). The leaderboard row and the profile carry `persona: { slug, displayName }` through `PersonaTags`. Its write twin **`OpsPersonasController`**: `POST ops/personas/batch` (≤ 100 per call) — upsert by slug, links merged by URL, each Riot ID resolved to the tracked account on its platform (the resolver's case-insensitive, most-recently-active rule) or stored as published and, with `seedMissing`, queued through the seed intake on a platform the pipeline ingests — elsewhere it is stored and answered `untracked`, never seeded, and the batch logs those once (#2134); a placeholder name or tag (`undefined`, `null`) is answered `invalid`. Additive only (a source that stops listing something unlinks nothing); an account another persona holds is answered `conflict`, never moved, and recorded in `persona_account_conflicts` for the admin's queue (#2253) — a repeat claim bumps its count; a claim an operator settled against the persona is answered `excluded` (`persona_account_exclusions`), and an entry sent under the slug of a persona merged into another feeds the kept one (`personas.MergedIntoPersonaId`, answered with `mergedInto`); every upsert retries the persona's unresolved accounts, which is how a seeded account ends up linked. Fed by an ops scraper kept outside the repo, like the OTP seeder. The conflict queue (#2253): `GET ops/personas/conflicts` (paged, `status`/`source`/`region`/`search`, open/resolved counts; each row's `evidence` — shared social kinds, shared reference pages, differing social kinds, `score` — from `PersonaConflictConfidence`, and `status=Open` ranked by that score, in memory since the open queue is small), `GET ops/personas/conflicts/{id}` (both personas in full, every account and link with its source) and `POST ops/personas/conflicts/{id}/resolve` — `move` (the account goes to the claimant, the former holder is excluded), `keep` (the claimant is excluded), `detach` (off the holder, both excluded) or `merge` + `keep: claimant|owner` (accounts, links, exclusions and open conflicts move to the kept persona; the merged one stays as an empty row pointing at it, so `GET players/{slug}` answers the kept persona and the web page 301s there). One transaction under the API's retrying execution strategy (`PersonaConflictResolutionService`), audited as `resolve_persona_conflict`. The operator's management (#2019, `OpsPersonaEditsController`): `GET ops/personas` (paged, `view` = `All`/`Conflicts`/`Unresolved`/`Removed`, `source`, `search`; per row tracked/untracked accounts, links, open conflicts — `PersonaAdminQueryService`), `GET ops/personas/{id}` (accounts and links with row ids and sources, exclusions with their reason, removed links, open conflicts), `POST ops/personas` (manual add through the intake with source `Manual`, name locked; 409 on any slug ever used), `PATCH ops/personas/{id}` (rename, locks the name: `personas.DisplayNameLocked`), `POST|DELETE ops/personas/{id}/links[/{linkId}]` (a removed URL goes to `persona_link_exclusions`, which the intake skips; adding it back lifts it), `POST ops/personas/{id}/accounts` (through the intake, after lifting the persona's own exclusion of that account) and `DELETE ops/personas/{id}/accounts/{accountId}` (unlink: an exclusion without a conflict, and the open claims on it are dropped), `DELETE ops/personas/{id}?takedown=` (`PersonaRemovalService`: the row and slug stay with `RemovedAtUtc`, accounts, links and open conflicts go; the intake answers `removed: true` for the slug and writes nothing; a takedown writes `IsTakedown` exclusions the intake applies to every persona). Merged or removed personas answer 409 to every edit. Each edit is audited (`create_persona`, `rename_persona`, `add_persona_link`, `remove_persona_link`, `add_persona_account`, `unlink_persona_account`, `remove_persona`; target `Persona`, best effort). Same-name known players (#2271, `OpsPersonaHomonymsController`): `POST ops/personas/conflicts/auto-merge` settles as merges the open conflicts whose two personas share a name key (`PersonaHomonyms`: lowercased, without spaces, dots, dashes, underscores), into the older persona, audited `resolve_persona_conflict` with actor `auto` — then merges the same-name personas sharing a social channel (#2286), each connected group into its oldest, skipping a group with a pair marked different (`mergedByChannel`, actor `auto`, `merge_personas`) — the intake runs the same sweep (`PersonaAutoMergeService`) after every batch, and `PersonaAutoMergeStartupSweep` once 30 s after the API starts (#2273); `GET ops/personas/channel-conflicts` (#2286, `OpsPersonaChannelConflictsController`: pairs of live personas listing the same social channel — kind + `PersonaConflictConfidence.ChannelKey`, decoded in memory by `PersonaChannelConflictFinder` — not marked as different people, most channels first, `search`, both personas in full; derived, never stored, and counted in `GET ops/personas`' open conflicts and `Conflicts` view); `GET ops/personas/homonyms` (paged groups of live personas sharing a key, `search`, the groups with a link two members share first — `sharedLinks`, keyed by `PersonaHomonyms.LinkKey` — personas oldest first, with the pairs already marked); `POST ops/personas/homonyms/merge` (`keepId`, `mergeIds`: the conflict queue's merge, `PersonaMerger`, shared by all three; a merged link whose channel the kept persona already lists is dropped, #2286) and `POST ops/personas/homonyms/distinct` (`personaIds`: every pair to `persona_distinct_pairs`), audited `merge_personas` / `mark_personas_distinct`.

**The cockpit reads are kept warm (#2305).** Pipeline health (30 s TTL), the data-quality detectors (1 min), the Overview counters (2 min), the aggregation stats (2 min) and the patch coverage (5 min) each sit behind a `WarmPayload<T>` (`Api/Services/WarmPayload.cs`): a value inside its TTL is served as is, an older one is still served at once — every payload carries its own computed-at time, which the admin prints — and only a payload with no value at all (never computed since the API started, or unread for 24 h) makes the caller wait. `CockpitCacheRefresher` (`Api/Services/Ops/`, a hosted service registered by `AddWarmPayload`) ticks every 5 s and recomputes the most overdue payload once it reaches 75 % of its TTL — one at a time, through the same single-flight as the request path, so a refresh and a cold request never run the same computation twice — and only payloads read within the last 15 min: an admin nobody has open costs nothing. A failed refresh keeps the last good value and its computed-at time, and opens the payload's failure backoff (#2132), which the refresher respects too.

**Pipeline-health alerting (#2292).** `PipelineHealthAlerter` (`Api/Services/Ops/Alerting/`, hosted, registered with the cockpit) evaluates the `/health` payload every `Alerting:EvaluationInterval` (5 min) — read through `WarmPayload.GetUnreadAsync`, so it reuses a fresh value, computes one otherwise, and never counts as the read that keeps the refresher busy — and posts to a Discord webhook (`Alerting:DiscordWebhookUrl`) on transitions only: a signal red for `RedConfirmations` (2) evaluations in a row, a process at `ProcessFailureThreshold` (3) consecutive failed runs, and their recoveries, with a per-key `Cooldown` (1 h). The first evaluation after boot only observes; the state (`health_alert_state`, versioned, saved before sending) survives deploys; each alert is recorded in `health_alerts` and served by `GET /ops/health-alerts`. No webhook → off, and the configuration page's *Health alerting* section shows `Enabled`, never the URL.

**Every champion read is cached and coalesced through one door (#1368).** `IChampionReadCache` (`Api/Services/Champions/ChampionReadCache.cs`) is the only way a champion query service answers: it looks in the shared memory cache, joins the pass already running for the same key, or runs the read once for everybody (`RequestCoalescer`). Entries are keyed by the **aggregation version** — the newest `AggregatedAtUtc` over `champion_aggregate_scopes`, read behind a 5 s cache and single-flighted — instead of expiring on a 60 s clock, so an aggregate-backed answer lives until the ingestor actually publishes new numbers (~1–2 h). The reads that fold `match_participants` live (synergy trios, the live matchup branch, mains-comparison, composition) also move with match ingestion, which the token does not track — for those the 30-minute absolute expiry is the freshness bound, knowingly. Scaling left that list when #1368 moved it onto `champion_scaling_stats`. Before it, five reads (`builds`, the live matchup fold, synergy trios, `trend`, and the since-removed `patch-diff`, #1466) had no cache at all and only the truemains leaderboard coalesced. `ChampionReadCacheRegistrationTests` fails if a service the champion controller resolves takes a raw `IMemoryCache` or no cache at all.

Cross-cutting: memory cache (`SizeLimit = 1024`, no Redis), global per-**visitor** rate limit (`RateLimit:*`, 500 req/min by default, keyed on the forwarded client address rather than the connection — #1546; rejections are logged, #1555), `/healthz` + `/readyz`, RFC 7807 problem details with `traceId`, 5xx answers and client aborts logged with their path and that `traceId` (#1555), HSTS outside dev, CORS that fails boot when unset outside dev, OpenAPI/Scalar **Development-only**.

**Scope filters are rejected, not ignored (#1224).** A non-blank `?eloBracket=` that is not a bracket (`GOLDD`, `UNRANKED`, `gold_minus`) is a **400**, exactly as an unrecognised `?position=` already was. It used to resolve to "no restriction" — the same answer as `ALL` — so a typo served the whole population's games under a rank label, a fabricated number rather than a lenient filter. Blank still means every bracket. The query services carry the same rule as a safety net for callers arriving without MVC: `EloBracket.ResolveFilterOrEmpty` degrades a rejected filter to *no band at all* (an empty read), never to every band, and such a filter gets its own cache token so it can neither be served from nor evict the `ALL` entry. The web app normalises the value client-side before it leaves the browser, so the rank picker cannot produce a 400. The player-scoped performance panel applies the same rule to its own lane filter, which it previously passed through raw.

**A player's matchup search reports a real share (#1224).** The player-scoped `?opponent=` lookup used to force its denominator to zero, so `playRate` came back as 0 — "a matchup this player never plays", out of a head-to-head they asked for by name — while the aggregate path had been fixed in #1098. Both paths now count the whole field they are a share of: for a player, every lane-opponent game on that champion and lane, before the opponent narrowing and before the per-player games floor.

**The pace benchmark (#1912)** — `GET /benchmarks/pace?position=` (`Api/Services/Benchmarks/PaceBenchmarkQueryService.cs`), read by the desktop overlay only: per tier and whole minute (1–30) of a lane, the sample and the p25 / median / p75 of a laner's cumulative CS (minions + monsters) and gold earned, read off `pace_benchmark_stats` histograms pooled over the newest three patches. A minute under 50 samples carries its count without quartiles. Every tier is returned so the app picks the player's own locally. One cache entry per lane, one hour.

**The form benchmark (#2076)** — `GET /benchmarks/form?position=` (`Api/Services/Benchmarks/FormBenchmarkQueryService.cs`), read by the desktop dashboard only: per tier of a lane, the games sampled and the p25 / median / p75 of a laner's end-of-game KDA, kill participation (0–1), CS/min, deaths and vision/min, read off `form_benchmark_stats` histograms pooled over the newest three patches. A tier under 50 games carries its count without quartiles. Folded with the pace benchmark, from the same games (regular ingestion and `PaceSampling`). One cache entry per lane, one hour.

### Ingestor
**Each run records the `Job:Mode` its pass was running** (`process_runs.jobMode`, surfaced on both ops read models). The lane a run is drawn under comes from its process name, so this is not what groups the chain; what it answers is what the pass was *supposed* to run. A deliberate single-process run (`MatchDataRetentionOnly` and friends) is otherwise indistinguishable from a lane that has only reached its first step, and the panel draws it as just the step that ran rather than as a lane with eleven skipped chips.

**Two lanes since #1362.** `JobMode.FetchLane` (LadderSync → Discovery → ManualSeed → Harvest → Scoring → MainActivity → MatchIngestion → AccountRefresh → PaceSampling) and `JobMode.AggregateLane` (TeamPositionCorrection → RoleBoundItemBackfill → MainAnalysis → EloBracketEnrichment → PatternAggregation → the seven folds → MatchDataRetention → ChampionGameCountRefresh → CandidateStockSnapshot → StorageSnapshot) are composite modes like `Full`, and together they are exactly `Full` (asserted by a test). **Both environments run them as two containers** — an `ingestor` on the fetch lane, back-to-back, and an `ingestor-aggregate` on a 20-minute timer (`truemain-ingestor{,-aggregate}` on prod since #1490, `truemain-preprod-ingestor{,-aggregate}` since #1374). Orphaned-run reconciliation at boot is scoped to the booting lane's own steps, or two lanes would abandon each other's live runs.

**Permanent fetch workers since #1457.** `JobMode.FetchWorkers` owns exactly the fetch lane's steps but runs `MatchIngestion` out of the sequence: one permanent worker per regional routing value (`americas`/`europe`/`asia`, from `MatchIngestion:Platforms`) claims a batch of its own platforms' accounts (`MatchFetchWorkers:BatchSize`, unset = `MatchIngestion:BatchSize` split across the routes), fetches match + timeline, writes, and claims again — idle `IdleDelaySeconds` after an empty claim, `FailureBackoffSeconds` after a failed batch (or one whose every account failed). The rest of the lane runs beside them as a **maintenance pass** on `Job:IntervalMinutes` (1 min in both compose files, so it runs at least as often as the old back-to-back lane). Each batch is its own `process_runs` iteration, stamped `FetchWorkers` like the maintenance passes; the admin draws a batch as a separate **Fetch workers** branch and the maintenance pass as the fetch lane without `MatchIngestion`. Throughput is the current stage of `MatchFetchWorkers:RampStages` (30 → 36 → 40 → 44 calls/min per regional host, `RampStage` 1 by default = production's average before the change, raised one held-and-measured stage at a time per `docs/ingestion-ramp.md`, #1459), enforced by the rate limiter as a ceiling on the `MatchIngestion` caller per routing value; **resource backpressure** (#1459) reads the host's available memory (`/proc/meminfo`) and free disk before every claim and holds the claims while either is below `IngestionBackpressure:MinAvailableMemoryPercent` (10) / `MinFreeDiskPercent` (15), until it recovers `ReleaseMarginPercent` above — a batch already claimed always finishes, and each activation and release is an ops event (`IngestionBackpressureActivated` / `Released`); `DrillMinutes` holds it for a set time from the first claim to verify it live; `RiotRateLimit:ReservedShares` (AccountRefresh 5 %, ManualSeed 2 %) holds a share of every regional window back from the workers while its owner is active and hands it back after `ReservationLingerSeconds`. A worker reaps and releases only its own platforms' claims, and a batch a shutdown cancels releases its claims on the way out; the boot's orphan release still runs for the mode. `Job:RunOnce` means one maintenance pass plus one batch per worker. Both deployed fetch containers run `FetchWorkers` (`INGESTOR_JOB_MODE=FetchLane` restores the sequential lane).

`Worker.cs` is a `BackgroundService`: reconcile orphaned `Running` rows to `Abandoned` at boot and release the claims the previous incarnation was holding (#1513 — a single instance per lane cannot have a live claim at boot, so the accounts a redeploy interrupted are claimable again immediately instead of a `MatchIngestion:ClaimLeaseMinutes` later), then loop {`RunOnceAsync(mode)` → stop if `Job:RunOnce` (default true) else wait `Job:IntervalMinutes`} — under `FetchWorkers`, with the match-fetch workers running beside that loop for the host's lifetime. The liveness file the Docker healthcheck reads is refreshed every 30 s by its own loop that spans the worker's whole lifetime (#1229), not once per iteration. A failed iteration is logged and counted, never fatal. The mode concept is **`JobMode`** — `Full` expands to the ordered pipeline below, any other value runs that single process. Each process is DI-keyed by its `JobMode` and wrapped in `RecordedProcess` (writes `Running`, heartbeats, then `Success`/`Failed` + serialized summary — or `Cancelled` when a shutdown cuts the run short, which is what a redeploy does; the deployed lanes get a 120 s `stop_grace_period` to unwind, #1513).

**Riot client layer** — typed clients (match / platform / account), each wrapped in three handlers, outermost first: the standard **resilience** handler (total timeout, retry honouring `Retry-After`, circuit breaker, per-attempt timeout — its "rate limiter" strategy is a concurrency bulkhead and paces nothing), then the **rate-limit observer** (#1359), then the **metrics** handler, with the **rate limiter** itself wrapped around all three. The limiter holds one budget per Riot routing value (`europe`/`americas`/`asia`, `euw1`/`kr`/`na1`) because that is the grain Riot meters, learns its limits from `X-App-Rate-Limit` / `X-Method-Rate-Limit` (so a production key needs no redeploy), reconciles against the `-Count` headers, and freezes the right bucket on a 429. Configured under `RiotRateLimit:*`, shown on the admin configuration page. The wait sits **outside** the resilience handler and the header feedback **inside** it: inside, a permit wait would be charged to the 10-second per-attempt timeout and fail the call (it did, on preprod, within an hour of the first deploy); outside, the observer would never see the 429s the retry strategy absorbs. Metrics stay innermost, so a permit wait is not recorded as Riot latency and every physical attempt including retried 429s is still recorded to Mongo. The limiter's own permit waits and 429s, and the worker's swallowed run failures, are instruments of the `TrueMain.Ingestor` meter, folded per minute into Mongo by `IngestorMeterExporter` (#1636). The limiter's, match ingestion's and the account loops' log lines are `[LoggerMessage]` source-generated methods (#1636).

**Mongo** (`truemain_logs`, TTL retention): `logs` (90 d, lossy bounded channel), `audit_events` (lossless, synchronous, read by `GET /ops/audit-events`, indexed on time and on (target type, target id, time), #2288), `riot_api_call_rollups` (30 d, #1458), `crashes` (365 d, file-first then Mongo, with unclean-shutdown detection for OOM kills), `db_table_size_snapshots` (365 d, one document per table per day, day-keyed upsert so the pipeline's many daily runs refresh rather than append), `process_runs` (180 d TTL, recorder-written run documents read by the admin process panels and Discovery's cadence gate), `seed_requests` (no TTL — functional admin queue: API inserts Pending, ManualSeed claims atomically), `process_boots` (#2297, append-only: every Api and Ingestor container writes its version — the deploy's `APP_VERSION`, passed as `AppVersion` — and start time at boot via `ProcessBootRecorder`, flagged `versionChanged` against that process+role's previous versioned boot; a partial TTL expires restarts after 30 d, deploys are kept for good; read by `GET /ops/deployments?from=&to=`, which lists the version changes only). Their frozen SQL tables were dropped in #1244.

**One cohort behind every champion panel (#1365).** `Data/Aggregation/ChampionCohort.cs` is the single predicate the folds that write the champion page compose — matchups, lane outcomes, synergies: *tracked account, `main_champion_stats.IsMain` for the champion being played, canonical `TeamPosition`, and a game of at least 5 minutes* (remake floor — Riot's `gameEndedInEarlySurrender` is not stored). Only the **queried** side is narrowed: opponents and synergy partners stay whoever was in the game. A unit test greps the fold sources so a new inline filter cannot slip back in, and an integration test folds one corpus containing a main, a tracked non-main and a remake, asserting the header, matchups and synergies all report the same denominator. The re-fold that shipped it covers the live patches only, across its tables (the matchup one for the remake clause alone) — frozen patches keep the pre-#1365 numbers.

**Compiled model** in `Data/CompiledModels/` is committed and auto-discovered (no `UseModel()` call) — regenerate with `dotnet ef dbcontext optimize` after any schema change.

**Region balance** — the match-ingest claim and the harvest budget are split per platform by coverage deficit
(`PlatformBudgetAllocator`, `weight = 1 + MeanDeficit(platform)`), not by a configured per-region quota. Coverage
itself is keyed on (platform, champion). Floors, not partitions: an unfillable share spills round-robin. The claim
logs its allocation each run; there is no admin panel for it yet.
**BuildFacts** (`Data/BuildFacts/`) is the build-derivation shared by Ingestor and API: item metadata provider, boots/final-build/starter resolvers, skill-order builder, and `FinalInventory` — slots 0–5 plus the role-bound slot, the one input every resolver reads (the trinket slot never is, #1612).

### Core
Dependency-free domain layer: `DedicationScore` (the Truemain score, 0–100, play rate + Riot mastery, #1701), `MainAnalysisOptions` (the main-analysis contract shared by Ingestor and API), Riot identifiers/routing, map & queue types (`LolQueueId`, `LolPosition`, `QueueDataQualityProfile`, `TeamPositionInferrer`), ranking (`EloBracket`, `RankScore`), and **`MatchPerformanceRanker` / `PerformanceScore` / `PerformanceScoreInput`**.

> ⚠️ **A per-match performance score already exists and ships.** `MatchPerformanceRanker` is consumed by
> `Api/Services/Truemains/{MatchDetailQueryService,MatchSummariesQueryService,PlayerChampionPerformanceQueryService}.cs`;
> it is what produces the **MVP/ACE accolade** on collapsed match rows. Unit-tested in
> `tests/TrueMain.UnitTests/{MatchPerformanceRankerTests,PerformanceScoreTests,PerformanceInputsTests}.cs`.
> #918 must therefore **extend and surface** this scorer, not build a new one.
>
> **Shipped in the first #918 PR** — the model is documented in [`docs/performance-score.md`](../../docs/performance-score.md):
> eight role-weighted components (combat, KP, damage share, gold share, farming, vision, **laning** ≤15 min,
> **mid game** >15 min), fed by the whole canonical-mark lead curve (5/10/15/20/30) instead of a
> single @15 diff. (A ninth, **roam**, shipped with it and was removed with the rest of the roam axis — see
> decisions.) `PerformanceScore.Explain`
> returns the per-component breakdown. Input assembly is centralised in `Api/Services/Truemains/PerformanceInputs.cs`
> so the match feed, the detail page and the player-champion panel cannot grade the same game differently.
>
> **Still open on the epic**: the peer-relative radar — it needs a role + rank baseline aggregation
> (percentile per component within a bracket) that does not exist yet, and rule-based badges on top of the
> same inputs.
