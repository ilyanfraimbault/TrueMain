## web/ — public site (Nuxt 4 + Nuxt UI v4)

No `layouts/` dir; the shell is `web/app/app.vue` (`AppHeader`, `NuxtPage`, `AppFooter`). **Dark-only** — no colour-mode toggle; the colour-mode `storageKey` was moved so stale `light` preferences retire.
All data goes through the catch-all proxy `web/server/api/[...path].ts` → `NUXT_API_BASE_URL`.

### `/` — `web/app/pages/index.vue`
Hero + search field, **two** live stat chips (main games analysed, truemains tracked), a tier-list teaser (`home/TierlistPanel.vue`, top 8, rendered eagerly with `home/TierlistPanelSkeleton.vue` while loading), a truemains teaser with region switch (`home/TruemainsPanel.vue`), CTAs. Both chips and the teaser read `GET /champions/overview` (`useChampionOverview()`, #972) — a homepage-sized snapshot (games-analyzed total across every aggregated row, not just the ranked ones; pre-sorted top rows) instead of the full `/champions` directory.
**Both chips are lifetime totals, printed compactly and without a patch qualifier**: `gamesAnalyzed` is one SQL `SUM` over every `champion_aggregate_scopes` row on the tracked queue, all patches (`GetTotalGamesAsync`, cached 30 min), and the truemains count is the leaderboard's global total. `formatCompactCount` (`shared/utils/counts.ts`) shortens them — `490,365` → `490k`, `1,204,886` → `1.2M` — always rounding **down**, so the printed figure is one the data clears. The teaser below stays on the served patch alone: a tier is a percentile inside one patch's field. The former third chip ("N champions ranked") and the patch-window labels (`over 16.15–16.14`, #1109) are gone — see `decisions.md`.

### `/champions` — `web/app/pages/champions/index.vue`
Champion/lane directory, one row per (champion, position) — capped at each champion's **two dominant lanes** (#1082, see below), so ~270 rows rather than 5 × N. Filters: role, champion, elo, **truemains**, patch. Elo defaults to **Master+** (#1346, `DEFAULT_ELO_BRACKET`), not "All ranks"; the resting URL carries no `?elo=` and picking "All ranks" pins `?elo=ALL`, which is now a deliberate choice rather than the absence of one.
**The default patch is the newest one that can actually fill a directory (#1109)**, not simply the newest one holding an aggregate row: a patch needs `ChampionsList:MinServablePatchLines` (50) `(champion, lane)` lines past `MinSampleGames` before the patch-less reads default to it, and the resolver walks back a patch at a time until one clears the bar. Shared by the directory, the tier list and the homepage, all of which resolve through `ChampionSummariesQueryService`. The served patch is reported in every row's `patchVersion` and drives the patch picker, so the fallback is visible rather than silent, and the thin patch stays explicitly selectable. Set the bar to 0 to restore the pre-#1109 rule. Each row shows keystone + secondary tree, consensus build path (6 items max), tier badge, WR/PR/**BR**.
**BR (ban rate, #920)** is lane-independent — the same value on every row of a champion — and shows an em dash, never `0%`, on patches predating ban ingestion. Tiers are pickRate + banRate + winRate, weighted toward presence (pick 45% / ban 30% / a sample-shrunk win rate 25%) and ranked by percentile within each lane — see `ChampionTierCalculator` (#971).
**Dominant lanes only (#1082)**: `ChampionDominantLaneFilter` keeps each champion's `ChampionsList:MaxLanesPerChampion` (2) most-played lanes, and a *secondary* lane only if it carries `ChampionsList:MinSecondaryLanePlayRate` (10%) of the champion's games. The most-played lane is always kept, so no champion disappears. Applied in `ChampionSummariesQueryService` after the sample floor and **before** tiering, so it lands identically on `/champions`, `/champions/tierlist` and the homepage teaser, and a lane's tier percentiles rank only the champions genuinely played there.
Pagination and search are **client-side** (the endpoint returns the whole directory in one payload, `PAGE_SIZE = 50`). Body wrapped in `<ClientOnly>` with skeletons; all fetches `server: false` deliberately (hydration-mismatch fix, #149).

### `/champions/tierlist` — `web/app/pages/champions/tierlist.vue`
Server-computed tier list, over the same dominant-lane rows as the directory (#1082 — a champion appears at most twice, on its two dominant positions) and carrying **the directory's own tier**: since #1240 the endpoint only regroups the `Tier`/`TierScore` `ChampionSummariesQueryService` already stamped per lane, instead of running `ChampionTierCalculator` a second time over the same rows with the same options. The two endpoints can therefore no longer disagree on a champion's letter — an integration test compares them row by row. One `SectionCard` per tier group (S→D), each a wall of champion portraits linking to the champion page (`ChampionTierChip`). Filters: role, elo, **truemains**, patch — the same Master+ default as the directory. A chip is the portrait alone, with its lane badged into the bottom-right corner; the name and `Win rate / Pick rate / Ban rate` live in the hover tooltip, values coloured on the `--color-data-*` axis by `app/utils/rate-tone.ts` (same ban-rate caveats as the directory). The link's `aria-label` carries name + lane + the three rates, since no tooltip opens on touch or for a screen reader.

### `/champions/:slug` — `web/app/pages/champions/[slug].vue`
The richest page — two columns at `xl`.

- **Header** (`Champion/Header.vue`, shared with the player-scoped page) — portrait, `h1` name, a small warning triangle carrying the **thin-sample caveat** in its tooltip when the slice is under `ChampionsList:MinBuildSampleGames` (#1346 moved it here from a full-width alert, and dropped the bracket-coverage clause it used to carry — see `decisions.md`), then the lane as its **position icon** (label in a tooltip and in the `alt`, so Riot's raw `UTILITY` is never shown) · games · WR. While the aggregate is in flight the title and the stat line render as **skeletons** rather than the placeholder read `Champion {id} · UTILITY · 0 games · 0.0% WR`; the name is sourced from the SSR-resolved `/api/static/{id}` fetch (not the client-only statics), so the server HTML still carries the real `h1` and the title only skeletons on client-side navigation. The `notEnoughData` state keeps the numbers — there, the zeroes are the answer. A **`Roamer` badge** sits at the end of that stat line when the champion's average out-of-lane K+A by 15 min clears `ROAMER_KP15` (1.5, `utils/roam-verdict.ts`), with the figure in its tooltip; below the threshold, unmeasured, or `JUNGLE` ⇒ no badge at all. That badge is the **whole** surface of the roam metric — the three-bar panel it replaced is gone (see decisions) — and it only renders on the champion page, which is the only one that fetches `/roam`.
- **Build tabs** (`Champion/BuildTabs.vue`) — one pill per build, **up to 4** (`ChampionBuildDisplayCaps.MaxBuilds`), most played first, each above 5% of the champion's games. Every dimension inside a tab lists its **top 3 variations** (`ChampionBuildDisplayCaps.MaxVariations` — spells, starters, skill order, boots; rune pages keep their own top 3), and since #1466 only **when there is more than one to list**: `variationOptions` (`shared/utils/build.ts`) filters on a 10% pick-rate floor (5% until then), caps at 3, and returns nothing at all when a single option survives — so a settled category renders no card and a champion whose build is not up for debate renders no variations section. The dominant option of every category is in the core block regardless, which is why the single-option card was a restatement rather than an alternative. Both caps are shared with the `?vs=` matchup fold since #1240 — they were 4 tabs / 3 variations on the aggregate path against 3 / 5 on the matchup one, so picking an opponent silently removed a tab and added two variations, as if the filter had changed what a build is. The caps describe the component, not the data source; the aggregate path's values won, because a matchup slice holds 4 games at the median and a fourth or fifth variation there is a single game rendered as a trend. Still literals for now — #1241 migrates the build thresholds to `ChampionsListOptions`. While the aggregate is in flight the section renders `Champion/BuildTabsSkeleton.vue`, which is **these same tabs in `pending` mode** over a placeholder aggregate (`app/utils/build-placeholder.ts`): the loading picture is the loaded layout with unresolvable ids, so every icon shows the pulsing box `SkeletonImage` already draws while a real icon loads and every number is masked. The two loading phases the page cannot merge (waiting on the API, then waiting on the ~95 DDragon icons) therefore look like one continuous state instead of two different pictures — see decisions. `Champion/BuildCoreSkeleton.vue` is the core-view-only counterpart for the composition builder; `pages/dev/build-skeleton.vue` renders both with nothing to fetch. Each panel (`Champion/BuildPanel.vue`) contains:
  core section (spells, starter items, skill order, boots, build path, runes), **build tree**, **variations**, **rune variations**, and **power spikes** (`BuildPanel/Powerspikes.vue` — hand-drawn bars, Items/Levels toggle; only when both `championId` and `position` are set). The item bars are **the tab's own core build path, in build order** (#1021): the event rows are keyed on the build but hold every item each game completed, so the read intersects them with the core path resolved by `ChampionCoreBuildPathResolver` (the same list the core panel renders) and returns them in its order. No path resolvable ⇒ item bars withheld, levels still shown. Each bar's minute is that item's mean completion over the games where it was built, so the bars do **not** share a denominator and the row is not one game's timeline — conditioning the minutes on the preceding core items is #1022.
- **Why this item** (#1451) — every item hover card on the page (`GameTooltip/ItemBody.vue`) carries the **situational build context** measured by #1450 under the item's own tooltip: a class line — `Situational` or `Core item` — and, when situational, up to three lines of the shape *"62% against a magic-damage team"*. Deliberately just the rate and the situation: the contrast rate, the sample size and the scope footnote were all cut (#1465) because the class already says the pick is situational and the card is read in a hover, not studied. The **key term carries the item tooltip's own colour vocabulary** — magic damage in the magic-resist cyan, physical damage in the armour orange, following Riot's rule that damage is coloured by the resistance that blocks it (`tooltip-parser/tag-classes.ts` is the source of that convention); terms with no stat behind them — melee, ranged, a strong laner — stay uncoloured, because a card where every other word is tinted says nothing. A `Preference` renders **nothing at all**: true, but not worth a line on three quarters of all items. The wording of every axis lives in `shared/utils/item-context.ts`; an axis this build has no phrase for is dropped rather than printed raw, and a vitest suite fails when the fold gains an axis with no copy for it. The low end of an axis is worded as its own situation — an item built against ranged lanes reads *"against a mostly ranged team"*, never a negation. The cards reach the **build tree**, the **core view**'s build path, boots and starter, and the **boots / starter variation rows**; tree nodes carry no mark of their own (#1465 removed the situational ring). One fetch per tab set (`useChampionItemContext` in `Champion/BuildTabs.vue`) rather than one per tab, keyed on (champion, position, patch) and deliberately not on rank or opponent.
- **Build summary** (`Champion/BuildSummary.vue`, #1123, typeset in #1143, hover cards in #1147, collapsed in #1466) — the build **in words**, at the **foot** of the right sidebar (below Truemains, Matchups and Compare with mains) inside a **closed native `<details>`**, and the only build content in the server-rendered HTML (every panel around it is `server: false`). Sentences come from `shared/utils/champion-build-summary.ts`; the ids are resolved to names by `server/api/champion-summary/[championId].get.ts` (5 min `defineCachedFunction` — an hour until #1273, which was long enough for the prose to name a different patch, and a different sample, than the live panels beside it — ~3 kB payload — ~1 kB of names plus one icon URL each, 844 B gzipped) because naming an item needs the ~373 KiB client-only item map. Describes `builds[0]` — the tab the page opens on — and carries the **same scope as the panels**: the `?vs=` matchup filter is forwarded (without it the prose described the global build under panels re-sliced to the matchup) and `minSampleMet: false` adds the low-sample caveat the header shows as a warning icon. Every sentence is a measurement: a clause whose data is missing is dropped, an id DDragon doesn't know is dropped rather than labelled, and the whole section renders nothing when there is nothing to measure. Visible, never `sr-only`. #1143 gave it relief: the sentences are built as **tokens** (`championBuildSentenceTokens`), so every named entity renders with its own 16 px icon inline and a tone — items gold, runes in their tree's colour (`--color-rune-*`), measurements set bold and tabular — and no sentence uses an em dash. The plain sentences are the tokens concatenated, so the decorated paragraph and the indexable one cannot drift. Each mark (`Champion/BuildSummaryMark.vue`) also triggers the **same hover card as the icon grid** — item, rune, summoner spell and ability — resolved client-side from the static maps the page already fetches, so the payload doesn't grow and the cards simply appear at hydration. Rune *trees* and the pinned opponent get no card: the tree tooltip elsewhere is only its own name, which the sentence has already said. #1466 then cut the runes, skill-order and summoner-spell sentences — each named in words a row of icons already on screen — and closed the section by default: native `<details>` rather than `UAccordion`, because Reka unmounts closed content and the paragraph has to stay in the SSR HTML. ~110 words on a well-covered champion — short of the 150-300 the issue estimated, because the remaining words would have been padding rather than data. Rationale and the SSR round-trip trade-off in `decisions.md`.
- **Below the fold**, all lazy + `hydrate-on-visible` with frozen props (`useLazyHydrationSnapshot`, the #834/#837 scroll-jank fix):
  - `Champion/TrendChart.vue` — **winrate & pickrate by patch**, two area charts over the last 5 patches (cross-patch by design; the patch filter is not forwarded). A third **ban rate** chart appears only once at least two patches carry ban data (#920); its series is filtered to those patches rather than drawn with gaps.
  - `Champion/ScalingChart.vue` — winrate by game-length bucket, with a verdict badge ("Scales late" / "Early game") shown **only outside the ±3-point dead zone** and carrying the label alone (#1466): inside the band it rendered `−2.7% Even`, a signed decimal on a measurement the word beside it had just called insignificant, and outside it the curve already carries the magnitude.
  - `Champion/Synergies.vue` — **duo & trio synergies** (#922). Best teammates ranked by *observed − expected* win rate (never raw pair WR), with a `RolePicker` narrowing the partner lane (the champion's own lane is excluded). Picking a partner expands the best third picks for that duo underneath. Every row carries its sample, with how often the pairing actually happens in the games tooltip; the three insufficient-sample cases (no champion baseline / no partner past the shared-games floor / duo too thin to split) each get their own sentence with the real count — no fallback numbers. **Two more floors since #1090**, after the panel's best synergies turned out to be 21-game pairings led by "Sylas BOTTOM": `ChampionsList:MinSynergyPlayRate` (1% of the champion's games, combined with `MinSynergyGames` by taking the larger) drops pairings that are merely rare, and `ChampionsList:MinSynergyPartnerLanePlayRate` (10% of that partner's ally games across all lanes) drops pairings whose partner does not play that role at all. Trios get the lane filter, not the share floor.
- **Sidebar**: top-10 truemains on the champion (`useTruemainsLeaderboard(…, { server: false })` — the panel is lazy + `hydrate-on-visible`, which defers *hydration*, not server rendering, so until #1231 it quietly made `GET /api/truemains?championId=…` the page's second SSR round-trip; the leaderboard skeleton is the server-rendered state now, and `server: true` stays the default for `/truemains` and the homepage teaser, where the leaderboard is the content); **matchups** (best 5 / worst 5 + specific-opponent picker) with a **Lane / Game** win-rate split (#919 — lane WR counts only *decided* lanes, i.e. a gold gap past `LaneOutcomeAggregation:GoldLeadThreshold` at 15 min, so its sample is smaller than games and shows an em dash rather than 0% when no lane was decided; the lane tooltip also carries the **average gold gap at 15 min** and its own smaller sample, #976). Reworked end to end by #1087, which found the panel ranking noise: it is **scoped to the page's patch** (it silently wasn't, and its aggregate outlives the matches it was folded from, so it spanned four patches under a header showing one); the leaderboard drops anything under `max(ChampionsList:MinMatchupGames, ChampionsList:MinMatchupPlayRate × the champion's total matchup games)` — an absolute floor alone is meaningless across champions 1000× apart in volume; best/worst are ranked on the **Wilson bounds** (lower for best, upper for worst) rather than the raw rate, so eleven games at 82% no longer outrank 739 at 57%; the lane column has its own `MinDecidedLaneGames` floor, since its sample is ~58% of the games beside it; and every row **links to `/matchup`** with both champions and the role pinned. The `?opponent=` search is served from the same aggregate rows as the list with **no floor at all**, so the two can no longer disagree on the same matchup (they did, 22 vs 13 games) and lane counters can no longer outnumber the games they sit next to. Only the player-scoped route stays live and cross-patch (the aggregate has no account dimension, and a patch filter would empty a single player's panel), and it keeps lane data null — a population-wide aggregate is not one player's lane. **Mains comparison** (`Champion/MainsComparison.vue` — enter a Riot ID, compare WR/KDA/CS·min/gold·min against all mains or one chosen main).
- **Truemains toggle** (`Champion/TruemainToggle.vue`, #1346) — sits next to the rank select on the champion page, the directory and the tier list. **On by default**: the numbers are folded only from *mains* of the champion, which is the population the aggregate held exclusively before #1346. Off (`?everyone=1`, `?truemainsOnly=false` on the API) widens to every tracked player with games on the champion — a strict superset, not a swap. **The non-main rows only exist once `MainAnalysis:AggregateNonMainPopulation` is turned on** (default false, #1349): until then both states return the same games, because the pipeline still folds mains only. Carries the `AppLogo` M-check mark drawn at icon size in `currentColor` (never the rose-gold ramp: a gradient that stays lit would keep reading as "on", and its own `<defs>` id would collide with the logo's), with the label beside it so the control still reads without knowing the brand, and a **two-part `UTooltip`** (its `#content` slot, the `RateBadge` idiom — not the flat `text` prop): a title naming the population currently shown (`Truemains only` / `Every tracked player` / `Locked to truemains`) over one line saying what it is and what flipping it does, so a reader who only takes the title still learns which games they are looking at. It **locks on while a matchup is pinned** — that slice comes from a mains-only aggregate, and the API 400s the combination rather than serving mains-only rows under an "everyone" label; the filter composable also resolves the pair away, so a hand-edited `?vs=…&everyone=1` renders the matchup instead of erroring. Not rendered on the player-scoped champion page: its scope is already one account. The population is part of every cache key it touches — `useChampion`'s data key (without it the toggle flips with no refetch and the two populations share an entry), the SSR build-summary route's, and the backend's summaries cache.
- **Header population** (#1466) — the stat line names the cohort the counts come from (`824 games played by mains` / `across all tracked players`), so the truemains toggle (#1346) is legible without hovering its tooltip.
- **Matchup filter** (#923): an opponent picker sits in the filter bar next to role/elo/patch (`?vs=<championId>`), and picking one **re-slices every build section** — variations, core, build tree, runes, skill order — from the games where the two champions actually met. It is not an aggregate read: `champion_matchup_stats` has the opponent but no build data, and the pattern aggregates have the build data but no opponent, so this path folds `match_participants` live (`ChampionMatchupBuildsQueryService` + `LiveBuildVariationAggregator`, sharing `ParticipantBuildFactsLoader` with the `/matchup` tool so a game means the same build to both). The core moves with the slice because it *is* the most played value inside it, and the fold serves **the same 4 tabs / 3 variations** as the unfiltered page (#1240) — the filter changes which games are counted, never how much of the build is shown. Note the one cap that still differs on purpose: the matchup fold applies **no 5% pick-rate floor** (2026-07-30 — the honest answer to a thin slice is its game count, not a hidden section). Selecting an opponent pins the displayed position (the backend matches both sides on it and 400s without one); a matchup with no game in the retained window renders the no-data state. Every variation carries its game count — measured on production, the median champion-vs-opponent pair holds 4 games on a patch, so the volume has to travel with the percentages; it now rides in `RateBadge`'s hover tooltip — Games / Pick rate / Win rate on their own labelled line each — rather than sitting inline next to the two chips, which kept the rows scannable without losing the sample. **Power spikes** re-slice too (#957), but by a different route: their per-game magnitude needs the dense per-minute grid that retention prunes, so nothing can recompute them live — instead the aggregation now records the lane opponent it already measured each spike against, and the read filters on it (`?opponentChampionId=` on `/powerspikes`, no games floor, same 2026-07-30 rule). Two consequences to know. Only matches folded since #957 carry an opponent, so a matchup's spikes start empty and fill in patch by patch, and the section says *"No game of this matchup has been measured for power spikes yet"* rather than blaming the matchup. And the two halves of the page count **different populations**: the live build fold takes every participant who faced the opponent, while the powerspike aggregation folds the shared champion cohort — mains of the champion, remakes excluded (`Data/Aggregation/ChampionCohort.cs`, #1365; it was the wider "any tracked account" until then) — so the spikes' game counts sit below the build tab's on the same matchup. Pre-existing — #923 is what widened the build path — and left as is rather than narrowing the builds or widening the aggregate, but each spike carries its own count so neither number is presented as the other's.

### `/matchup` — `web/app/pages/matchup.vue`
A **live matchup tool** (reworked by #921, renamed from `/builder` by #939 — the old route still redirects, query preserved), not a build editor. Centre stage (`builder/MatchupStage.vue`): your champion, your role and the **role opponent** as large portrait-sized pickers — the matchup is the primary input because the API treats the pinned role opponent as a hard filter on the sampled games. The copy says *role* opponent, never *lane* opponent: a jungler has no lane (#939). Composed as one centred block with **no card around it** (#1063, #1065, #1067, #1069): the two portraits facing each other across the matchup icon, then the role strip underneath on the same centre line. Every other block on the page is a `surface` card, so a card here put the subject of the page on the same footing as its two supporting panels. Role reads second because that is the order the picks are made in — it gates every fetch, but it is one choice among five against ~170 champions. **The portrait *is* the control**: clicking either one opens `builder/ChampionSlot.vue`'s champion-only command palette (the `AppSearch` interaction minus the truemain and browse groups, `LazyUCommandPalette` so the chunk loads on first open). The `ChampionPicker` selects it replaced were the loudest thing in the stage — a wide combobox wrapping a single word — while the portrait beside each carried no interaction at all; `ChampionPicker` stays in `TeamContext` for the eight secondary draft slots, where a portrait grid would out-shout the matchup.

The block carries **no on-screen text at all** (#1067, #1071): no micro-label over each tile, no champion-name caption, no role name, no page description, no "required" hint. The splash art names the champion better than a caption repeating it, each role button carries its own icon, and every accessible name lives in an `aria-label` where it costs nothing visually. Ownership reads from the accent alone: your tile's ring is `primary`, the opponent's neutral. Hover/focus is ring-colour and cursor only — an earlier scrim-and-magnifier overlay was removed as noise. The clear × is `variant="subtle"`, never `solid`: on a dark-only theme neutral-solid is white, which put the brightest thing in the block on top of the art it annotates. Clearing is offered twice: an inline × on a filled tile, and a `Clear` row pinned in the palette (`ignoreFilter`, so a mistyped search can still be undone in one step). While no champion *and* role are picked the page shows a one-line dashed placeholder instead of the stage alone over an empty screen. Below it, secondary and quieter (`builder/TeamContext.vue`): the eight remaining draft slots (4 allies / 4 enemies, the played role omitted since the stage owns both sides of it), which only re-weight the similarity search — with no helper line, the section reads as optional on its own. The component folder keeps its `builder/` name on purpose (`components/matchup/MatchupStage.vue` would auto-resolve to `<MatchupMatchupStage>`).
All three matchup inputs are **deep-linked** (`?champion=&position=&opponent=`) so a matchup is shareable; the eight context slots stay ephemeral. No submit — every edit refires after a 400 ms debounce through `useCompositionBuild()` → `POST /api/champions/{id}/composition-build`, keeping the previous result dimmed on screen and dropping out-of-order responses.
The recommendation's core panels and build tree carry the same **why this item** cards as the champion page (#1451), read from the champion's aggregate scope — the verdicts are not folded per opponent, so they describe the champion at large rather than the entered draft; highlighting the axes a draft actually matches is a follow-up of #1447. The standard-build fallback carries them too, which is where they are most useful: it renders precisely when the matchup has no games.

Output (`builder/RecommendationPanel.vue`): low-confidence warnings (the sample strip it used to open with merged into the stat line above in #1111), the same core panels as the champion page (`Champion/BuildPanel/Core.vue`, the one block all three build surfaces render), and the build tree. **No power spikes, no variations, no rune list, no situational-items row** — #939 removed the latter (front *and* API) because the build tree already shows the same off-core items with their ordering.
**One line of numbers** (`builder/MatchupStats.vue`, #1111): a four-cell strip directly under the stage — **games used**, **draft match**, **win rate** and **lane win rate**, the last carrying the average **gold** and **XP gap at 15 min** on a line beneath it plus the verdict badge (Very good / Good / Even / Bad / Hard **lane**, or *matchup* at `JUNGLE`, which has no lane). **All four describe the same games** since #1117: the lane cell is judged live over the recommendation's own selection (`CompositionLaneOutcomeQueryService`, returned as `lane` on the composition-build response), not read from the matchup aggregate. It used to be the aggregate, whose champion side is mains-only (#1087), which showed `—` beside "8 games used · 0 by mains". Each cell still prints its own denominator, because the three counts differ: games sampled, lanes *measurable* (both sides need a 15-min snapshot), lanes *decided* (outside the gold threshold band).

## admin/ — operator portal (standalone Nuxt app, `ssr: false`)

Separate app with its own deployment and domain — **not** a `/admin` route of `web`.

**Auth & backend access.** Single-operator username/password → sealed httpOnly session (`nuxt-auth-utils`); no user store, no roles. `admin/server/api/auth/login.post.ts` does a constant-time compare with a per-IP throttle (5 attempts/60 s). Every route is gated by `admin/app/middleware/auth.global.ts`. That middleware only runs on navigation, so an **expiry while parked on a page** is caught instead by a global `$fetch` interceptor (`admin/app/plugins/session-expiry.client.ts`): a 401 from `/api/ops/*` or `/api/static/*` clears the session and redirects to `/login` once, however many panels were mid-flight — before #1225 the dashboard just turned red with "Failed to load" and read as a backend outage.
**All backend traffic goes through one proxy**: `admin/server/api/ops/[...path].ts` requires the session, then forwards to `${opsApiBaseUrl}/ops{path}` injecting the secret `X-Ops-Key` **server-side** — the ops key never reaches the browser. Its containment guard (`server/utils/proxy-path.ts`, the same file in `web/`) rejects a path that could leave the backend, judged on the decoded path as well as the raw one. A boot plugin refuses to start outside dev with default credentials, short secrets, or an admin password under 12 characters.

**Captions and info popovers.** Since #1414 every panel header goes through `components/PanelTitle.vue`: a
title, at most **one line** of caption under it, and an `i-lucide-info` button opening a `UPopover` that holds
everything longer — the method notes, the measurement caveats, the chart footnotes. Nothing was deleted, only
relocated, so a caption that used to run four lines (Candidates throughput, the candidate-level curves, queue

## backend/ — .NET 10 solution

### Api
Three controllers, all delegating to injected `I*QueryService` — no EF types cross the controller boundary; read models are `sealed record`s under `Api/ReadModels/`.

- **`ChampionsController`** (public): list, tierlist, `overview` (#972 — homepage snapshot: lifetime games-analyzed total + top rows), detail, trend, patch-diff, matchups, synergies, synergies/trios, scaling, item-timings, roam, powerspikes, mains-comparison, `POST composition-build`, and `POST composition-build/games` (#940 — the recommendation's provenance drawer, paged).
- **`TruemainsController`** (public): search, leaderboard, profile, player-scoped champion + matchups + **performance**, rank-history, **activity** (#927 — the four-granularity grid in one payload, no mode param), matches, match detail.
- **`OpsController`** (`X-Ops-Key` auth): 28 endpoints backing the admin portal.

**Every champion read is cached and coalesced through one door (#1368).** `IChampionReadCache` (`Api/Services/Champions/ChampionReadCache.cs`) is the only way a champion query service answers: it looks in the shared memory cache, joins the pass already running for the same key, or runs the read once for everybody (`RequestCoalescer`). Entries are keyed by the **aggregation version** — the newest `AggregatedAtUtc` over `champion_aggregate_scopes`, read behind a 5 s cache and single-flighted — instead of expiring on a 60 s clock, so an aggregate-backed answer lives until the ingestor actually publishes new numbers (~1–2 h). The reads that fold `match_participants` live (roam, scaling, item timings, powerspikes, synergies, the live matchup branch, mains-comparison, composition) also move with match ingestion, which the token does not track — for those the 30-minute absolute expiry is the freshness bound, knowingly, until part B pre-aggregates them. Before it, five reads (`builds`, the live matchup fold, synergy trios, `trend`, `patch-diff`) had no cache at all and only the truemains leaderboard coalesced. `ChampionReadCacheRegistrationTests` fails if a service the champion controller resolves takes a raw `IMemoryCache` or no cache at all.

Cross-cutting: memory cache (`SizeLimit = 1024`, no Redis), global per-IP rate limit 100 req/min, `/healthz` + `/readyz`, RFC 7807 problem details with `traceId`, HSTS outside dev, CORS that fails boot when unset outside dev, OpenAPI/Scalar **Development-only**.

**Scope filters are rejected, not ignored (#1224).** A non-blank `?eloBracket=` that is not a bracket (`GOLDD`, `UNRANKED`, `gold_minus`) is a **400**, exactly as an unrecognised `?position=` already was. It used to resolve to "no restriction" — the same answer as `ALL` — so a typo served the whole population's games under a rank label, a fabricated number rather than a lenient filter. Blank still means every bracket. The query services carry the same rule as a safety net for callers arriving without MVC: `EloBracket.ResolveFilterOrEmpty` degrades a rejected filter to *no band at all* (an empty read), never to every band, and such a filter gets its own cache token so it can neither be served from nor evict the `ALL` entry. The web app normalises the value client-side before it leaves the browser, so the rank picker cannot produce a 400. The player-scoped performance panel applies the same rule to its own lane filter, which it previously passed through raw.

**A player's matchup search reports a real share (#1224).** The player-scoped `?opponent=` lookup used to force its denominator to zero, so `playRate` came back as 0 — "a matchup this player never plays", out of a head-to-head they asked for by name — while the aggregate path had been fixed in #1098. Both paths now count the whole field they are a share of: for a player, every lane-opponent game on that champion and lane, before the opponent narrowing and before the per-player games floor.

> Reads live in `Api/Services/<area>` as purpose-built query services injecting `TrueMainDbContext` and projecting read-models with `AsNoTracking` — no generic repository. That is the rule as decided in #865, not a divergence from it; see [decisions.md](decisions.md#where-api-reads-live).

### Ingestor
**Each run records the `Job:Mode` its pass was running** (`process_runs.jobMode`, surfaced on both ops read models). The lane a run is drawn under comes from its process name, so this is not what groups the chain; what it answers is what the pass was *supposed* to run. A deliberate single-process run (`MatchDataRetentionOnly` and friends) is otherwise indistinguishable from a lane that has only reached its first step, and the panel draws it as just the step that ran rather than as a lane with eleven skipped chips.

**Two lanes since #1362.** `JobMode.FetchLane` (LadderSync → Discovery → ManualSeed → Harvest → Scoring → MainActivity → MatchIngestion → AccountRefresh) and `JobMode.AggregateLane` (TeamPositionCorrection → MainAnalysis → EloBracketEnrichment → RunePageDedup → PatternAggregation → the five folds → MatchDataRetention → StorageSnapshot) are composite modes like `Full`, and together they are exactly `Full` (asserted by a test). Preprod runs them as two containers — `truemain-preprod-ingestor` on the fetch lane, back-to-back, and `truemain-preprod-ingestor-aggregate` on a 20-minute timer; **prod still runs a single `Full` container** until preprod has proven the split. Orphaned-run reconciliation at boot is scoped to the booting lane's own steps, or two lanes would abandon each other's live runs.

`Worker.cs` is a `BackgroundService`: reconcile orphaned `Running` rows to `Abandoned` at boot, then loop {`RunOnceAsync(mode)` → stop if `Job:RunOnce` (default true) else wait `Job:IntervalMinutes`}. The liveness file the Docker healthcheck reads is refreshed every 30 s by its own loop that spans the worker's whole lifetime (#1229), not once per iteration. A failed iteration is logged and counted, never fatal. The mode concept is **`JobMode`** — `Full` expands to the ordered pipeline below, any other value runs that single process. Each process is DI-keyed by its `JobMode` and wrapped in `RecordedProcess` (writes `Running`, heartbeats, then `Success`/`Failed` + serialized summary).

Pipeline order (`Full`) — the 21 steps of `Ingestor/Options/JobModeSequence.cs`, in that exact order. The
sequence is the source of truth; renumber this table from it, never the other way round.

Joins entries against `riot_accounts` and **never inserts** | **Before** Discovery, so the rank snapshots the later EloBracketEnrichment step reads are this cycle's. | 3 | ManualSeed | Drains pending seed requests (admin "Add mains"), promotes straight to `Queued` | After Discovery, **before** Scoring: it queues directly, skipping the competitive top-N, so a seeded account is picked up by the same run's MatchIngestion → MainAnalysis pass |

**Riot client layer** — typed clients (match / platform / account), each wrapped in three handlers, outermost first: the standard **resilience** handler (total timeout, retry honouring `Retry-After`, circuit breaker, per-attempt timeout — its "rate limiter" strategy is a concurrency bulkhead and paces nothing), then the **rate-limit observer** (#1359), then the **metrics** handler, with the **rate limiter** itself wrapped around all three. The limiter holds one budget per Riot routing value (`europe`/`americas`/`asia`, `euw1`/`kr`/`na1`) because that is the grain Riot meters, learns its limits from `X-App-Rate-Limit` / `X-Method-Rate-Limit` (so a production key needs no redeploy), reconciles against the `-Count` headers, and freezes the right bucket on a 429. Configured under `RiotRateLimit:*`, shown on the admin configuration page. The wait sits **outside** the resilience handler and the header feedback **inside** it: inside, a permit wait would be charged to the 10-second per-attempt timeout and fail the call (it did, on preprod, within an hour of the first deploy); outside, the observer would never see the 429s the retry strategy absorbs. Metrics stay innermost, so a permit wait is not recorded as Riot latency and every physical attempt including retried 429s is still recorded to Mongo.

### Data
`TrueMainDbContext`, 30 `DbSet`s. Tables by domain:
- **Identity**: `riot_accounts`, `personas` (half-built, unused), `main_candidates`, `discovery_cursors`
- **Raw matches**: `matches` (carrying `Patch`, a **stored generated column** holding the `major.minor` of `GameVersion` — indexed `(Patch, QueueId)` and `(QueueId, Patch, PlatformId)`, #1368), `match_participants`, `match_participant_timeline_snapshots`, `match_participant_kill_positions`, `match_bans`, `participant_perk_selections`, `perk_selection_catalog` (item/skill events are jsonb, not tables)
- **Aggregates**: `champion_aggregate_scopes` (account × champion × patch × platform × queue × position × elo bracket) + `champion_aggregate_patterns` (one row per observed build+runes+skills+spells+starters combo), with content-deduplicated `champion_dim_{builds,rune_pages,skill_orders,spell_pairs,starter_items}`. Rune pages store their two **secondary** perks in canonical (ascending id) order — the player's click order made the same page two rows and split its sample (#911)
- **Derived**: `main_champion_stats`, `champion_matchup_stats`, `champion_synergy_stats` + `champion_synergy_baseline_stats`, `champion_ban_stats` + `ban_scope_totals`, `champion_profile_stats` (#1449, measured per-champion profiles), `champion_item_context_stats` + `champion_item_context_totals` + `champion_item_context_verdicts` (#1450, situational build context), read by `GET /champions/{id}/item-context` (#1451 — no `eloBracket`, no `truemainsOnly`, no `opponentChampionId`: the verdicts carry none of those dimensions, so each would be a filter that silently does nothing), `champion_powerspike_{curve,event}_stats`, `powerspike_sigma_stats`
- **Snapshots / ops**: `rank_snapshots`, plus the frozen `process_runs` / `seed_requests` leftovers below

**Mongo** (`truemain_logs`, TTL retention): `logs` (90 d, lossy bounded channel), `audit_events` (lossless, synchronous), `riot_api_call_rollups` (14 d), `crashes` (365 d, file-first then Mongo, with unclean-shutdown detection for OOM kills), `db_table_size_snapshots` (365 d, one document per table per day, day-keyed upsert so the pipeline's many daily runs refresh rather than append), `process_runs` (180 d TTL, recorder-written run documents read by the admin process panels and Discovery's cadence gate), `seed_requests` (no TTL — functional admin queue: API inserts Pending, ManualSeed claims atomically). The SQL `process_runs`/`seed_requests` tables are frozen leftovers pending a drop migration.

**One cohort behind every champion panel (#1365).** `Data/Aggregation/ChampionCohort.cs` is the single predicate the four folds that write the champion page compose — matchups, lane outcomes, synergies, power spikes: *tracked account, `main_champion_stats.IsMain` for the champion being played, canonical `TeamPosition`, and a game of at least 5 minutes* (remake floor — Riot's `gameEndedInEarlySurrender` is not stored). Only the **queried** side is narrowed: opponents and synergy partners stay whoever was in the game. A unit test greps the four fold sources so a new inline filter cannot slip back in, and an integration test folds one corpus containing a main, a tracked non-main and a remake, asserting the header, matchups, synergies and power spikes all report the same denominator. The re-fold that shipped it covers the live patches only, across all four tables (the matchup one for the remake clause alone) — frozen patches keep the pre-#1365 numbers, and power spikes go thin on the live window while it refills (pruned timelines, #772).

**Compiled model** in `Data/CompiledModels/` is committed and auto-discovered (no `UseModel()` call) — regenerate with `dotnet ef dbcontext optimize` after any schema change.

**Region balance** — the match-ingest claim and the harvest budget are split per platform by coverage deficit
(`PlatformBudgetAllocator`, `weight = 1 + MeanDeficit(platform)`), not by a configured per-region quota. Coverage
itself is keyed on (platform, champion). Floors, not partitions: an unfillable share spills round-robin. The claim
logs its allocation each run; there is no admin panel for it yet.
**BuildFacts** (`Data/BuildFacts/`) is the build-derivation shared by Ingestor and API: item metadata provider, boots/final-build/starter resolvers, skill-order builder.

### Core
Dependency-free domain layer: `DedicationScore` (0–100 with exposed components), `MainAnalysisOptions` (the main-analysis contract shared by Ingestor and API), Riot identifiers/routing, map & queue types (`LolQueueId`, `LolPosition`, `QueueDataQualityProfile`, `TeamPositionInferrer`), map geometry (`Lol/Map`: `LolMap` zone classifier), ranking (`EloBracket`, `RankScore`), and **`MatchPerformanceRanker` / `PerformanceScore` / `PerformanceScoreInput`**.

> `tests/TrueMain.UnitTests/{MatchPerformanceRankerTests,PerformanceScoreTests,PerformanceInputsTests}.cs`.

>

> nine role-weighted components (combat, KP, damage share, gold share, farming, vision, **laning** ≤15 min,

> returns the per-component breakdown. Input assembly is centralised in `Api/Services/Truemains/PerformanceInputs.cs`
> so the match feed, the detail page and the player-champion panel cannot grade the same game differently.
